# 文档写作规则

本文档定义所有长期项目文档的写作要求。

## 1. 文档头信息

权威文档开头应尽量包含以下信息：

```md
> 文档角色：产品 / 设计 / 契约 / 当前实现 / 交付 / 笔记
> 是否真相源：是 / 否 / 任务期
> 更新触发：什么时候必须同步修改
```

## 2. 内容边界

- 产品文档写用户价值、能力范围、状态和验收标准。
- 设计文档写目标方案、模块职责、状态和设计取舍。
- 契约文档写跨模块稳定交互，不写长篇实现解释。
- 当前实现文档必须从源码反推，不写愿景和猜测。
- 交付文档写任务上下文、计划、进展、结果和遗留问题。
- 笔记文档写学习、解释、调研，不作为验收依据。

## 3. 状态标记

涉及未完成能力时，使用稳定状态词：

- `proposed`：提出想法，尚未排期。
- `planned`：计划做，但尚未实现。
- `in-progress`：正在实现。
- `shipped`：已经落地。
- `dropped`：明确放弃。
- `deprecated`：仍存在但不建议继续使用。

## 4. Agent 维护要求

- 更新 `40-implementation/` 前必须读真实源码。
- 更新 `30-contracts/` 前必须确认跨模块字段、事件或消息边界。
- 不要把 `90-notes/` 或历史归档当作当前行为依据。
- 发现文档与代码冲突时，先指出冲突，再更新唯一权威位置。
- 大范围重构文档结构时，先维护迁移映射，再更新入口和路径。
